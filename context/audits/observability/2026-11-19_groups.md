# Observability audit: groups (2026-11-19)

Scope: the **groups** flow, full stack. That covers the group page, the event plan and the
statistics page (`src/pages/groups/**`), child, event, attendance, driver and invite writes
(`src/pages/api/groups/**`), joining by invite (`/join/[token]`, `/api/groups/join`), the
`src/lib/services/*` they call, and the middleware every request passes through. Admin group
creation (`/admin/groups`) was skimmed and shares the same patterns.

Dirty tree at audit time: `.env.example` modified, plus untracked
`tests/e2e/declaration-plan.spec.ts` and `tests/e2e/support/`. None of these are audited code.

## 1. TL;DR

- **A Supabase Auth outage looks like a mass sign-out.** The middleware drops the error from
  `supabase.auth.getUser()`, so every `/groups/*` request redirects to `/auth/signin` with
  status 302 and no log line (`src/middleware.ts:20-23`).
- **Any 42501 / 0-row refusal becomes a silent 404.** This is deliberate, so the app doesn't
  reveal which groups exist. But the same branch also catches a broken RLS policy or a revoked
  `EXECUTE` grant, so a migration regression makes declarations "404" for every parent with
  nothing logged.
- **Every unexpected write failure becomes a 302 redirect** to `?error=unknown`. Status-based
  views in Workers Logs show success. The only signal is one unstructured `console.error` line,
  and nothing alerts on it (the user confirmed: Workers Logs only, no alerts).
- **Diagnosis is lost at the service boundary.** Services throw
  ``new Error(`X failed: ${error.message}`)`` without `cause`, and routes log `error.message`.
  The PostgREST `code`, `details` and `hint` are dropped on the read paths.
- **No log line names the group, event or user**, so a report like "my declaration won't save"
  can't be traced to an entity.

## 4. Systemic root causes

1. **The middleware treats an auth error as "signed out".** `src/middleware.ts:20-23` reads
   only `data.user`. `GoTrueClient._getUser` returns `{ user: null, error }` for every
   `AuthError`, including `AuthRetryableFetchError` for network failures and 5xx
   (`node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:2729-2735`, `lib/fetch.js:38-53`;
   **verified**). This is a reasonable "fail closed" choice, but it removes the only sign of an
   auth outage. Explains P-1.
2. **The "don't reveal the resource" 404 doubles as a catch-all with no log.** Every route maps
   42501 (and the 0-row UPDATE/DELETE result) straight to `rewrite("/404")`, or to
   `child_not_found` / `event_not_found`, and skips the `console.error`. Postgres also uses
   42501 for `permission denied for function/table`, so a broken grant takes the same silent
   path as a legitimate stranger. In `driver.ts:88-89` the code even comments "should not
   happen" on that branch. Explains G-1 and G-2.
3. **Failures are returned as redirects.** The PRG pattern (`redirect(?error=code)`) is right for
   form UX, but it means an unexpected database failure ends as 302 like any success. Explains
   G-3 and P-2.
4. **Services rebuild errors from `message` only.** 12 ``throw new Error(`…: ${error.message}`)``
   sites in `src/lib/services/*` have no `cause` (1 `cause` in the whole of `src/`). Callers
   then log `error.message` again (`attendance.ts:46`, `driver.ts:81`, `dashboard.astro:23`,
   `middleware.ts:35,45`). Explains G-4 and G-5.
5. **Log lines are fixed strings with no entity.** All 26 `console.error` sites log
   `"<op> failed:", code, message`, never `groupId`, `eventId` or `user.id`. Explains G-6.

## 6. Recommended fix order

1. **P-1: log and distinguish auth errors in the middleware.** One file, about 6 lines. It
   removes the biggest blind spot (a full outage that looks like logouts).
2. **G-1 + G-2: log unexpected refusals.** Add one shared helper,
   `logUnexpectedRefusal(op, error, ids)`, and call it on the forbidden/404 branches. Keep the
   user-facing 404 so group existence still isn't leaked. Constraint: never log the invite
   token, and log ids, not names or nicks.
3. **G-4 + G-5: keep `cause` and `code`.** A mechanical change to 12 throw sites and 4 catch
   sites. After it, every degraded-section and 500 log line says *why*.
4. **G-6 + G-3 + G-7: one structured log helper** (`logError({ op, event, groupId, eventId,
   userId, error })`) used by every route and page catch. With a stable `event` field, a single
   Workers Logs query or alert later covers all writes. Decide whether the `unknown` write
   branch should also change status (it affects the PRG UX, so it's a product call).
5. **P-2, G-8, P-3:** small follow-ups.

Error tracker: introducing one (e.g. Sentry for Cloudflare) would turn 2–4 into issues with
alerts. That's a vendor choice for `/10x-infra-research`. Fixes 1–4 are worth doing regardless,
because they decide what any tracker would receive.
